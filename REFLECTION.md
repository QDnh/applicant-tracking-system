## Project #1: Applicant Tracking System.

Question 1 - Trace your Django forms. Find one class in your project that inherits from forms.Form and one that inherits from forms.ModelForm. For each form, identify what it does and trace how it is used through the application. Explain the important difference between the two forms in your own words.

Q1.A Answer: I picked RecordApplicationFromJobForm (Form). RecordApplicationFromJobForm is in applications/forms.py on line 11. It appears on the job page, and consists of a dropdown list that contains the candidates able to apply for that job. JobDetailView is the view that creates the form, gives it the job, and passes it to the job page. The job page itself is what displays the dropdown. Pressing the record button on the job page takes the selection and POSTs it to RecordFromJobView, which checks it with is_valid(). If the selection passes is_valid(), RecordFromJobView calls Application.record() to create the application and redirect with a message. 

Q1.B Answer: I picked CandidateForm (ModelForm). CandidateForm is in candidates/forms.py on line 8. CandidateForm is the form used to create and edit a Candidate. It has the following fields: first name, last name, email, phone, source, and notes. It appears on the Candidate creation page and Candidate edit page. It has a clean_email() method that changes the email to all lowercase, and rejects the email if it finds another candidate already with that email. This check ignores case, and during editing, leaves the candidate out of the check to avoid detecting the candidate being edited. CandidateCreateView and CandidateUpdateView can use it through CandidateFormMixin. The Candidate create and edit pages display the form for user input. The submission is then checked by is_valid(), which runs clean_email(). Finally, CreateView or UpdateView calls form.save() to add the candidate to the database and redirects to the candidate's page with a success message.

Q1.C Answer: The primary difference is what saves the input data. RecordApplicationFromJobForm is only a Form, which only reads from the database, but doesn't handle saving data to the database. CandidateForm is a ModelForm and directly reads and writes to the database. CandidateForm saves data to the database directly with its save() method. Input into RecordApplicationFromJobForm is only validated and passed to other code, which does the saving.

Question 2 - Trace a many-to-many relationship. Identify a many-to-many or association-table relationship in your ATS. Explain which models are connected and why a single foreign key would not represent the relationship correctly. Identify the association table or model and explain whether Django created it automatically or your project defines it explicitly. If it is an explicit association model, explain what data belongs to the relationship itself.

Q2 Answer: I picked the many-to-many relationship between Candidate and JobOpening, with Application as an association-table. Application carries a "candidate" foreign key and a "job_opening" foreign key. This is required because a candidate can apply to many jobs, and a job can have many candidates. With only one foreign key, it would be a one-to-many relationship. The data of the relationship is stored in the Application association-table. My project defines this association-table explicitly. It holds stage, applied_at, and stage history. This data must be stored in the association-table because neither a Candidate nor a JobOpening can store this data alone.

Question 3 - Explain one prototype decision. Choose either your application-state prototype or your UI prototype. What specific design question was the prototype built to answer? Describe the alternatives you explored, the decision you made after using the prototype, and where that decision appears in your PRD or completed application.

Q3 Answer: My UI prototype was designed to answer how to display the stage data to the employees. I actually chose two of the three options. The first option was a table that displayed candidates under the job opening that they had applied for. The second option showed a Kanban format, which I immediately ruled out. I didn't like how it looked, and found it confusing to read when applications moved between stages. The third option was application cards that displayed all the job openings a candidate had applied for. I chose both options 1 and 3. I probably should have only chosen one option. That decision led to the implementation of both the job page and the candidate page.

Question 4 - Defend one code-design decision. Choose one architecture or code-structure decision from your project where the agent recommended one or more options. Explain the options, the decision you approved, and why that choice fits your project. Identify where that decision appears in the completed code.

Q4 Answer: One code-design decision that changed a key component was the difference between deactivated and archived. The agent recommended to make deactivated and archived the same status. I decided to propose a modified version of one of the other options that the agent had listed. I outlined that deactivated and archived should stay separate, which was the agent's second, nonrecommended option. However, I added that deactivated should be the lighter inactive state, and archived should be the heavier inactive state. Deactivated is for candidates we expect to reach out again. Archived is for candidates that we don't expect to reach out again, but we want to keep for records and in case the candidate does reach out. This fit the project because it allowed a way to hide candidates without deleting them and losing history data. This led to deciding that a candidate cannot be archived unless they have no active applications. The archive rules appear in candidates/models.py lines 15-18, which define the three statuses; candidates/views.py lines 29-31, which hide archived candidates from the candidate list; and candidates/models.py line 61, which is the rule that blocks archiving.
